# 原子能力图谱：把操作手册变成可执行的编排契约

> 对象：`D:\codeagent-minimal`（41 原子 / 165 能力 / 166 个 py，纯标准库）
> 基础：`docs/ATOMS_GUIDE.md`（操作手册，逐原子讲能力/入参/返回）+ `registry.json`（声明层）
> 日期：2026-10-23　｜　配套：`atoms_graph.html`（一张图）、`atoms_graph.json`（图数据）、`atoms_graph_report.md`（体检清单）

## 一、先说结论

1. **你的直觉是对的，而且比预想的更硬**：操作手册详讲的 17 个条目，和代码里真有调用路径的 17 个条目，重合 **16 个**。手册事实上已经是一张编排图，只是它躺在 Markdown 里，没有任何机制去执行它。
2. **这张图今天是星型**：73 个 `run_capability` 调用点（其中 32 个能静态解析出能力名），全部从 `AgentRuntime` 射出，**原子↔原子之间 0 条边**；`depends_on` 声明了 5 条，**一条都没被真调用**。所谓"依赖图"目前是装饰。
3. **"避免编排错误"的抓手不在图好不好看，而在图能不能当门用**：把三层数据源（声明 / 实现 / 调用）对齐，每有不一致就红，编排错误就只能显式登记、不能悄悄发生。
4. **图的第一性是完整性，不是活跃度**：41 个原子一个不省地画在同一圈上。24 个"零调用"原子是**完整可调、只是没有入口**的单元，不是残件；把它们画成外圈淡影，等于用编排覆盖度冒充原子质量。参见第十一节。

## 三、根因：不是"调用写错了"，是"根本不存在图"

现在防编排错误靠三样东西：`registry.json` 的字段、`agent_loader.py` 的拓扑排序、`codeagent.py status` 的健康输出。三者共同的问题是**只校验声明内部自洽，不校验声明与现实一致**：

- `agent_loader` 能发现"depends_on 指向不存在的能力"，但发现不了"depends_on 写的这条边，代码里从来没走过"（G3 就是这个洞）。
- `status` 能报 41 原子 ready，但 ready ≠ 可达。24 个零调用原子 ready 得很好，只是没有任何代码路径会调到它们。
- `AtomicAgent.call` 的 `except Exception` 把 `TypeError` 吞成 `{ok:false, degraded:true}`。**这是"编排传错参数"最容易被掩盖的地方**——上层看到的是降级，不是报错，根因（少传/错传参数）在日志里消失。G5 这条规则就是专门盯这个洞的；今天是 0，但如果没有门，明天改个签名就会静默变红。

**一句话**：不是"图没画好"，是"图没有执法权"。

## 四、图怎么建（三层对齐）

### 4.1 三层数据源

| 层 | 来源 | 提供什么 | 现状可信度 |
|---|---|---|---|
| **L0 声明层** | `registry.json` | 41 原子、165 能力、inputs/outputs、depends_on、order | 字段齐（41×12 全有），但 depends_on 全是空壳 |
| **L1 实现层** | `agents/*/*/main.py` 的 AST | `register("cap", self._fn)` 真实挂载 + 方法签名（可接受参数/必填参数） | 165 条全部可核（148 精确签名 / 14 个 `**kw` / 3 个 lambda） |
| **L2 调用层** | 全仓 `run_capability(...)` 的 AST | 谁在调谁、传了哪些 kwarg | 32 个可静态解析；41 个是动态能力名（`cap` 变量 / f-string），无法静态定 |

### 4.2 图数据（机读，`atoms_graph.json`）

```jsonc
{
  "schema": "codeagent-atoms-graph-v1",
  "nodes": [{
    "id": "dep-impact", "domain": "impact", "group": "质量验证",
    "version": "0.1.0", "provides": ["impact.analyze","impact.circular","impact.coupling"],
    "inputs": ["path","symbol","impact","transitive"],
    "outputs": ["files","entities","edges","coupling","circular_imports","impact"],
    "registered": ["impact.analyze","impact.circular","impact.coupling"]  // L1 实测
  }],
  "edges": [
    {"from":"<编排层>","to":"dep-impact","capability":"impact.analyze","kind":"call","count":2},
    {"from":"code-review","to":"dep-impact","capability":"impact.analyze","kind":"declared_dep","count":1}
  ],
  "findings": [{"rule":"G2_ORPHAN_CAPABILITY","severity":"P2","subject":"...","detail":"..."}],
  "metrics": {"topology":"star","capability_coverage":0.1636, "...": "..."}

```

边只有两种，够用：`call`（实际调用，L2 扫出来的）与 `declared_dep`（声称依赖，L0 写的）。**两种边对不上就是缺陷**，这是整套机制的支点。

### 4.3 画成"一张图"（`atoms_graph.html`）

一张图画四件事，读者不用看字也能得出判断：

- **所有线都从中心射出** → 星型拓扑，一眼看出没有原子协作
- **内圈实心 17 个**= 有真实调用边；**外圈空心 24 个** = 零调用
- **线宽** = 被调次数（`codereview.review` 7 次最粗）
- **颜色** = 六大域，同域聚成一段弧，看得出哪个领域整体休眠（安全治理 6 个全部休眠）

## 五、机制：让图有执法权（这是核心，图只是副产物）

### 5.1 五条硬约束（每条对应一类真实编排事故）

| 约束 | 拦的是什么事故 | 当前状态 | 处理方式 |
|---|---|---|---|
| **C1 只有声明过的能力可被调用** | 调用名打错/猜名（`doc.anchor` vs `docs.anchor`） | G1=0 | 硬红，阻断 |
| **C2 每个能力至少有一个可达路径，否则必须标 `dormant`** | 声明得很漂亮、谁也没用过（138 条） | 大量 | 硬红：要么补示例+调用、要么显式标休眠 |
| **C3 `depends_on` 必须被 `call` 覆盖** | 依赖写给人看、代码另有其事（5/5） | 全虚 | 硬红，或降级为 `advisory` 字段并要求写理由 |
| **C4 调用点实参必须落在目标签名内** | 传错参数被 `except` 吞成 degraded | G5=0 | 硬红（当前干净，靠门守住） |
| **C5 原子内跨原子调用必须登记 `depends_on`** | 隐式耦合，改一个炸一片 | 0（因为还没人这么写） | 硬红 |

G6 命名漂移（25 条）单独处理：它不阻断，但它是"人和模型猜错名字"的根源，规则设成 **同域内前缀必须统一**，新增能力不合规就红，存量进 baseline 台账（仓库已有 `config/constitution_baseline.json` 这套机制，直接复用）。

### 5.2 CI 第 5 道门

仓库现有四道门：`pytest` → `verify_download_ready` → `verify_evals + run_evals` → `constitution_gate_changed`。
图谱检查天然是第五道，而且和宪法门同构（只判改动文件 + 存量 baseline）：

```
scripts/verify_atoms_graph.py
  --repo . --baseline config/atoms_graph_baseline.json
  退出码 1 = 有未登记违规
```

三条实现纪律，避免这道门变成新的噪音源：

1. **只判改动**：新增/修改的原子与调用点严格判；存量的 138 条孤儿进 baseline，逐月收敛，不一次性要求全绿。
2. **负向验证入测试**：往 `tests/` 放一个故意传错参数的样本，断言检查器必须报 G5（我今天已经用迷你仓库验过：G1/G2/G4/G5/G6 五条规则在植入缺陷后全部如期触发）。
3. **门自己也进宪法门**：脚本本身受 `cc_max/嵌套/行长` 约束，防止检查器自己烂掉。

### 5.3 生成物（图不能手画，必须编译出来）

| 产物 | 内容 | 谁消费 |

## 六、社区对照：哪些已验证、哪些是坑

搜了一遍公开实践，结论高度收敛，且直接命中我们的三个症状：

1. **"死文档注册表"是被点名的头号反模式**（Schema Registries for Shared Tool Semantics）：条目准确、可搜索，但 agent 照样把工具清单硬编码，因为**没有运行时客户端**。症状就是"覆盖率遥测显示大量调用解析不到任何东西"。→ 我们正是：registry 齐全，调用全走硬编码 `run_capability("字面量")`。
2. **"条目与实现漂移"被要求用强制一致性测试兜住**（同上）：conformance test 不能是可选 dashboard，要当 incident。→ 对应 C4/G5。
3. **孤儿工具必须靠"调用方集合为空"判，而不是"调用次数低"**（MCP 生态治理面板）：`callers == empty` 才是孤儿，`calls < 90` 只是配置气味。→ 我们 24 个零调用原子正是 `callers == empty`，不是"用得少"。
4. **Agent Knowledge Graph 模式给了三条可直接抄的体检指标**：孤儿工具数、版本偏移（version skew）、遍历路径覆盖。→ 对应 G2、版本一致性（仓库已有 `test_version_consistency.py`）、可达性覆盖 16.4%。
5. **契约测试要在边界拦，不要只在终点拦**（Output Contracts / Contract Testing for AI Pipelines）：一条 10 步流水线，单步 95% 成功，端到端只剩 60%；且 AI 管道 64% 的风险在 schema 层。→ 支持把检查放在"每个调用点"（C4），而不是只在 `deliver` 出报告时校验。
6. **别上图数据库**：那套 Neo4j/Cypher 方案针对"上千工具、跨团队、需要语义检索"的场景。我们是 41 个原子、单仓、确定性——`json` + `networkx 式手写拓扑` 足够，引入图库只会增加一个部署依赖，违背"纯标准库、下载即用"的仓库底线。

## 八、明确不做的四件事

1. **不引入图数据库 / 外部依赖**。41 节点的图用 json + 手写拓扑排序足够，且 `verify_download_ready` 这条门要求零本机残留、纯标准库。
2. **不让 LLM 生成图**。图必须能从代码确定性重算；模型只能读图、不能写图，否则图本身就成了不可验证的幻觉源。
3. **不追求"全自动发现依赖"**。41 个调用点是动态能力名，静态分析有天花板（今天只能解析 32/73）。做法是：静态为主，动态兜底——`run_capability` 运行时把 `(调用方, 能力, 入参名)` 记进 `event-log` 原子，定期回灌图。这样图有两条腿，不会因为动态调用而瞎。
4. **不承诺"图能保证能力正确"**。它只保证**调用正确**（名对、参对、依赖登记对、可达性清楚）。能力本身对不对，仍然只能靠 `test/evals/fuzz`。这条边界要在手册开头写清，否则图谱会变成新的"看起来很安全"的错觉。

## 十、落点

这张图的价值不在"看见 41 个原子"，而在**逼着每个原子回答一个问题：谁在什么时候会调到你？** 答不上来的，要么补路径，要么老实标休眠。手册从"讲解文档"变成"编译源的图"，编排错误就从"靠人记"变成"过门"。

## 十一、图的第一性：完整性（2026-10-23 修订）

初版把 41 个原子画成内圈 17 个实心、外圈 24 个空心虚影，这在视觉上传递了一个错误信号：**"那 24 个是废件"**。实际上它们 registry 有登记、能力全挂载、`AgentRuntime` 直接可调 —— 缺的只是一条过来的路径。把编排覆盖度（17/41）当成原子质量（41/41），是两种账混在一起算。

### 判据：什么叫"一个原子是完整的"

三条，逐条可核对，当前全部成立：

| # | 判据 | 数据来源 | 结果 |
|---|---|---|---|
| ① | 登记在册（registry 有项、path 可解析） | `registry.json` | **41 / 41** |
| ② | 能力全挂载（`registered` 逐条覆盖 `provides`，不多不少） | `main.py` 的 AST 解析 `register()` | **165 / 165**，41 个原子逐条相等 |
| ③ | 入口可调用（main.py 能解析出注册表，非空壳） | 同上 | **41 / 41** |

三条都成立，就意味着**这个原子作为一个可调用的单元是完备的**；它有没有被调用，是另一本账。

### 画法：一个圆环，两种状态，一处叠加

- **41 个原子全部落在同一圈**（椭圆，周长足够摊开标签），按六大域切扇区。扇区弧带上写 `n/n 在位 · k 已接线` —— **分母永远等于分子**，这就是完整性在第一眼的读数。
- **主状态只有两种**，只描述"有没有入口"：
  - 已接线（17）：实心填充，实线连到中心，线宽 = 被调次数
  - 待接线（24）：淡填充 + 实描边 + 中心点 —— **插槽就绪**，与"坏掉"在视觉上明确区分；点线连到中心，表示路径还没走过
- **叠加一层欠账**：5 条声明 `depends_on` 声明了依赖、代码却没真调，用虚线外环标出（不改主状态，因为它们是欠账不是残缺）。
- 圆点大小 = 该原子声明的能力数。**孤儿原子也有大小**，因为它们的体量是真实的。

### 分工：完整性归图，覆盖度归表

- 图上不出现"覆盖率 16.4%"这类数字，避免用覆盖度给原子打分；
- 覆盖度、接线率、G2 命中数放在图下的**分域完整性表**里，明确标注为"编排覆盖度，不是原子完整度"；
- 每个待接线原子在表里单独列出（带能力数），确保"完整但在等路径"这件事落到个体，而不是一盘统计。

### 这条修订对机制的影响

CI 门与三态判定不变，但**报告口径要改**：G2 的命中不再表述为"孤儿"（暗示被遗弃），而是"未接线能力"，并在门里区分两种处置：补一条调用路径，或在 registry 显式标 `dormant: true`。**不标 dormant 又不接线，才算真正的欠账** —— 这才是那 24 个零调用原子该被追问的问题。

## 2 测试状态

### 2.1 本地 CI 总账

`python scripts/ci.py` 实跑结果：

```
36/37 绿（3 个固定步骤 + 34 扇 verify 门），用时 769s
红: pytest 全量
```

- 固定步骤：`pytest 全量` 红；`原子注册表重建` 绿；`原子全部 ready` 绿（`atoms=41 degraded=[] conflicts=[]`）。
- 34 扇 `verify_*.py` 门全绿，含宪法门（29 项断言）、成本回归、事件账本完整性与归档、六面审计、参数面自述（能力 165 个）、版本一致性等。
- `pytest 全量`：**3 failed / 354 passed**，耗时 699 秒。

### 2.2 三个失败与根因

三个失败同源：

```
tests/test_codeagent_atomic_agents.py:231  test_code_test_real_data_run
    assert tr["ok"] and tr["data"]["smoke"]["ok"]        → False
tests/test_codeagent_atomic_p1.py:106      test_code_test_real_run
    assert r["ok"] and r["data"]["smoke"]["ok"]          → False
tests/test_codeagent_fusion.py:100         test_test_real_file_smoke_passes
    TimeoutExpired: ['C:\Python312\python.exe','-m','pytest','-q',
      <tests/ 目录下 40 个测试文件全列>] timed out after 120 seconds
```

根因：`agents/test/code-test/project_verify.py` 的 `_run_unit()`，只要被测目录下有 `tests/`，就在该目录下**无参**跑 `python -m pytest -q --no-header`，于是 pytest 自行收集**全部**测试。调用方传 `target_dir=项目根` 时，等于把整个 `tests/`（40 个文件）当冒烟目标，而单次预算是 120 秒，而该项目全量 pytest 实测需要 699 秒。

**判定：这是产品侧真缺陷，不是「过期测试引用了被改名/合并的能力」那类重构假红。** 冒烟的本意是快速验证，把项目全量测试当冒烟目标，它对自己就永远超时。

### 2.3 修复方向（已按此派活）

1. `verify_project` 增加 `test_targets`：显式传入时只跑这些。
2. 未显式传入时按被测对象推断相关测试（`tests/test_<stem>.py` 优先），且目标数设上限。
3. **匹配不到就不退回全量**，unit 记为「未找到相关测试目标，跳过」，避免再次撞预算。
4. 调用侧（`agents/test/code-test/main.py`、`test_harness.py`）按同一语义同步。
5. 三个红测的断言一个字不改，必须靠真修复转绿。

## 3 三处硬伤

1. **可发现性为零。** GitHub 搜不到中文，无榜单收录、无对比数字，项目在检索层面等于不存在。
2. **无第三方信任凭证。** 检索到的唯一外部提及是 `10100.com`（大数跨境）2026-09-10 的《CodeAgent v0.4.1开源，外包代码值不值得信，它替你说了算》，内容为自家宣传口径的转载，**不是第三方评价，也没有第三方复现**。
   URL: https://www.10100.com/article/150619047
3. **版本口径自相矛盾。** 母体 README 同时出现版本 `v0.10.0`、badge `0.4.0`、文字说 38 个原子而后文又说 41 个；开源副本 `version.py` 为 `0.8.2`，README badge 却写 `0.8.1`。开源项目里这种不一致比功能缺口更伤信任。

---

## 4 下一步最该补的两件

**第一，版本一把尺子。** `version.py` 单点，README、badge、CHANGELOG 由它派生，并接进 CI 门做一致性断言（母体已有 `verify_version_consistency.py` 且绿，说明机制在，缺的是把 README / badge 也纳入断言范围）。

**第二，造一组第三人能复现的数字。** 在本机跑得动的范围里挑一个公开可比的口径（例如同一份外包代码上「查出多少真问题 / 误报几个 / 耗时多少」），附可复跑脚本。从「无人知晓」进到「可以被评价」是唯一门槛，star 数是结果不是手段。

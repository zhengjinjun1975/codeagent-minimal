## 一、出错的时候，谁说了实话

同一套调用，在两个版本上各跑一次（`AgentRuntime` 直接调，不经模型）。

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 能力名打错 `plan.thnik` | `ok=false`，**无错误码**，无候选 | `code=CAP_UNKNOWN`，并给出候选 `plan.think`、`plan.gen` |
| 参数传错 `bogus_key=1` | `degraded=true` —— 被当成"业务降级" | `code=CAP_CONTRACT`，`degraded=false`，列出 `unexpected=[bogus_key]` |
| 链上第 2 步能力名写错 | **`ok=true`，"通过 2/3"，第 3 步照跑** | `ok=false`，`halted_at=wrong`，第 3 步不执行 |
| 默认组合从哪来 | 没有这个 API，5 步链写死在 `codeagent.py` | `default_chain()` 从模板表读，5 步：think→gen→review→test→evolve |
| 模板占位符 `$task` / `$seed.k` / `$step.s1.f` | 原样字面量，一条都没解析 | 全部解析，嵌套 dict 也递归 |
| CLI `chain --template "排查/定根因"` | `error: unrecognized arguments` | 跑通，`全部通过`（think → archreview.layers） |

第三行是这次对比里最要紧的一条：**链上有个能力名是错的，旧版仍然返回成功。**
不是"没报错"，是"报了通过 2/3"。上面还在算覆盖率、算组合步数，下面已经把错的那步吞掉了。

## 三、门有没有假装看得见

这一节是本次对比里唯一的"退步"，也是唯一诚实的退步。

改动前 `scan_calls()` 遇到**变量能力名**直接 `continue`（旧版 `atoms_graph_core.py:248`）：

```python
a0 = node.args[0]
if not (isinstance(a0, ast.Constant) and isinstance(a0.value, str)):
    continue          # ← 不是字面量就丢掉，不留痕
```

后果：真实 44 个调用点里丢掉 12 个，对外报"可解析 32"，**盲区 0%**。

| | 改动前 | 改动后 |
|---|---|---|
| 真实调用点（AST） | 44（只报 32） | 45（全数进账） |
| 被静默丢弃 | **12** | 0 |
| 分级 | 无分级 | verified 30 / name-only 3 / **sealed 12** / blind 0 |
| 盲区比例 | 报 0%（实际 27%） | **报 26.7%**（sealed 计入看不见） |
| 阈值 | 无 | 黄 20% / 红 35% |

那 12 个 sealed 是这次为过宪法门拆函数拆出来的转发层（`_exec_step`、`_halt_on_contract` 等）。
**拆函数降低了圈复杂度，代价是多了一层对静态分析不可见的转发** —— 所以它们必须被声明
（`# dispatch-sealed:`）、必须被计数，而不是消失在 `continue` 里。

指标从 0% 变成 26.7%，不是变差，是终于开始说实话。

## 四、门抓不抓得住缺陷（变异测试）

往两个版本各注入同一批缺陷，看门会不会变红。判据只有一条：**注入后仍 pass，就是视而不见。**

| 注入的缺陷 | 改动前 | 改动后 |
|---|---|---|
| 代码里写死一条 2 步组合 `rt.run_chain(chain=steps)` | pass（无此规则） | **fail：G15 + G14** |
| 变量能力名转发器，不声明边界 | pass | **fail：G18** |
| 给零调用点能力改参数名（`resource_type`→`resource_kind`） | pass | **fail：G17** |

第三项特别说明：那个能力全仓 0 个调用点，改它的参数名以前**没有任何人会发现**，
连编译都不会报错。签名快照把这个方向堵上了。

## 五、端到端测试自己抓到的一个真缺陷

第一轮变异测试，写死链**注入后门仍然 pass**。查下来是老问题，不是这轮引入的：

`_is_run_chain()` 只认位置参数 `call.args[0]`。而 `rt.run_chain(chain=steps)` 语法上 `args` 是空的，
整个调用点被跳过。也就是说——**把链改成关键字写法（重构时最常见的动作），
G15 就再也看不见它了**，而 G15 是"组合只有一个源"的唯一守门人。

已修（`9cfed4d`）：新增 `_chain_arg()`，位置参数优先、其次 `chain=` 关键字；
`run_chain(None)` 与 `run_chain(chain=None)` 都判为自动选链，不误报。
配了两条成对测试：一条验它必须报红，一条验它不许误报。

这条是端到端测试的价值所在：**前面的单测、门、全量测试全绿，它照样存在。**
